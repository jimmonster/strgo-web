# STRGO Web 审查

先读 [架构](../../../doc/ARCHITECTURE.md)、[开发指南](../../../doc/DEVELOPMENT.md) 和 [最近审查](../../../doc/PROJECT-REVIEW.md)，再根据当前源码确认结论；不要直接沿用历史上线状态或测试计数。

## 覆盖项目边界

整仓审查覆盖根主站、`image_service/` 与 `apps/` 下六个应用。按任务抽查关键实现，明确哪些是结构检查、源码审查、离线测试和真实环境验收；无需逐行审查随仓库打包的第三方库。

- 集成：根构建从 `src/dreams/`、`src/nexus/` 取源，核对独立工程与副本；检查旧相邻工程路径、绝对服务器路径、挂载 base、直接访问和 404。
- 账号及存储：检查成员/管理员权限、其他用户资源、Cookie/Origin/CSRF、密钥暴露、外部请求地址限制、持久化与恢复。
- AI 空间：检查单独的模块/模型授权、管理 TOTP、报价版本、原子预算预占、唯一结算、SSE 重放、音频所有权及助手表单版本冲突；使用 [AI 接口与约束](../../../doc/ai/implementation.md) 核对部署前提。
- 任务：检查幂等、收费模型中断、上传重试、Workflow 租期与本机执行恢复，防止重复生成或覆盖已有数据。
- 终端：检查用户卷归属、WebSocket 会话失效、SSH 地址限制、代理访问边界与 Docker 参数；离线代码检查不能代表实际容器隔离已验收。
- 发布：检查版本校验、已有 Nginx 片段保留、失败回滚和持久化目录，不运行生产发布来证明静态检查通过。

## 验证和报告

先构建再运行依赖产物的测试。根 Node/Python 分开运行，各独立应用使用自己的脚本；部署回归使用临时样例，避免依赖本机生产配置。保留本地原始日志到忽略的 `artifacts/review/`，将可共享结论写入 `doc/PROJECT-REVIEW.md`。

每项发现记录优先级、源码位置、触发条件、用户影响、修复状态和验证证据。P0 表示紧急的广泛破坏或泄露；P1 表示应优先处理的越权、数据损失或关键链路失效；P2/P3 用于一般缺陷与改进。推测性风险和已复现缺陷分开列出。

用户授权修复时，对严重问题先复现、做最小必要修复并增加行为回归；范围较大的改进先写入后续事项。不得把缺少依赖、Bash、Rust、Docker 或浏览器导致的阻断写成测试通过，也不能据此判定线上业务已坏。

报告包含基准提交、日期、覆盖范围、已修复与未解决项、各模块验证结果以及生产验收缺口。用户要求上传 GitHub 时，检查最终差异仅包含本次改动后提交并核实远端状态。
